# Example: a WebFlux application that prints, fills, seals and verifies PDFs

`datum-spring-boot-starter-pdf` on Spring WebFlux. The server prints the answers of a form as a PDF, seals it with its
own key, and checks the signatures of any PDF it is handed. The form is a file on the class path
(`datum/forms/intake.json`); the page (`/`) is the renderer from `datum-spring-boot-starter-ui`.

## Before you build

The jars carry browser assets, programs and notices that the build generates from `packages/datum/dist`, so on a fresh clone
build those first. From the repository root, with Node 22 on the `PATH` (the Maven build runs `node`) and JDK 17 or newer:

```sh
npm run setup -- engine packages/quickjs-wasm-host packages/pdf-kernel packages/datum
npm run datum:build
```

The first Maven build also compiles the pinned QuickJS runtime for six native targets, which takes 12 to 16 minutes. Add
`-Pdev-native` to the `./mvnw` command below to compile the host's target only, for a local run. A source build is version
`0.1.0-SNAPSHOT`, the version in the jar name below.

## Run it

```sh
# All from integrations/jvm.
# 1. A development key store (RSA-2048, self-signed; always written to examples/webflux-pdf/local/dev-signer.p12,
#    wherever the script runs from; gitignored; never commit a private key):
examples/webflux-pdf/scripts/make-dev-keystore.sh
# 2. Build (the assets are generated by the build itself, into target/datum-assets) and run, pointing the SSL bundle
#    that holds the signing key at the file step 1 wrote:
./mvnw -q -B -pl examples/webflux-pdf -am package
java -jar examples/webflux-pdf/target/datum-example-webflux-pdf-0.1.0-SNAPSHOT-exec.jar \
  --spring.ssl.bundle.jks.pdf-signer.keystore.location=file:examples/webflux-pdf/local/dev-signer.p12
```

Open <http://localhost:8080/>, fill the form and send it; the confirmation links the receipt as a sealed, timestamped PDF.

## What the starter adds

Every route is off until switched on; this application's `application.yml` sets the five below to `true`. Each endpoint has its own switch:

| Endpoint | Does | Switch (`datum.web.api.endpoints.*`) |
| --- | --- | --- |
| `POST /api/pdf` | `{document, layoutId?, locale?, options?}`: the answers are judged first (the receiver's dry run, nothing kept), then printed | `pdf` |
| `POST /api/pdf/fill` | the same into a **template** layout; `template: {data: base64}` may carry the caller's pages | `fill` |
| `POST /api/pdf/sign` | the same, always sealed | `sign` |
| `POST /api/pdf/verify` | a posted `application/pdf` in, the signature report out | `verify` |
| `GET /api/server/certificate` | the server's signing chain, PEM, leaf first | `certificate` |

Answers carry `X-Page-Count`, `X-Datum-Layout` and, when sealed, `X-Signed-By`, `X-Signature-Field`, `X-Timestamped`.
Every endpoint is documented in the `datum-pdf` springdoc group when springdoc is present.

## Whose key seals what

* `GET /receipts/{id}.pdf` (this application's `ReceiptPdfController`) prints a **stored** submission through
  `PdfService.renderSubmission(...)`: a document the application issues, sealed with the server's key
  (`datum.pdf.seal.enabled=true`).
* `POST /api/pdf` and `/api/pdf/sign` print answers that were only *posted*: nothing stored them, so the server's key does
  not vouch for them. They are sealed with a throwaway test certificate (CN "Datum test seal - not valid") unless you set
  `datum.pdf.seal.posted-answers=true`, which you should do only where anyone allowed to post answers may have them
  certified by this server.
* A template the caller posts to `/api/pdf/fill` is never sealed with the server's key. Supply the application's own
  templates with a `PdfTemplateSource` bean.

## The timestamp authority

`datum.pdf.seal.timestamp=true` needs a source of tokens. This application runs its own: `datum.tsa.enabled=true` with the
throwaway self-signed certificate (`datum.tsa.signer.self-signed=true`, development only: it changes at every start and
nobody trusts it), and the serial numbers are rows of `datum_tsa_log` in the embedded H2 database, created at start by the
timestamp module's `V300__datum_timestamp.sql` migration, which `datum.jdbc.initialize-schema` (`embedded` by default) runs in the in-memory database (the in-memory allocator would be refused at start without
`datum.tsa.allow-memory-stores=true`; health reports `serials: jdbc`; beside `V100__datum_forms.sql` and `V200__datum_submissions.sql`,
which keep form snapshots and accepted-submission digests in the same database; a real application sets `never` and runs these scripts with
Flyway or Liquibase and a real key store). The PDF module asks the authority in process, so no HTTP request to `/tsa` is made for a seal; the route
exists for other callers, and because the example sets `datum.tsa.access=open` (no client key to hand out) the
`SecurityConfiguration` lets only callers on this machine reach it: a rule of the security chain
(`matchers(datum.tsa()).access(loopbackOnly())`, Spring Security's own address managers, the matcher following `datum.tsa.path`), whose
refusal is the wire's `access.denied` JSON. Behind a reverse proxy on the same host every request looks
local: set `access=clients` there and drop the rule. `X-Timestamped: true` on a receipt and the `timestamp` member of a
verify report (`coversSignature`, `verified`, `trust: site`) show the token is there and is this server's.

## Who may build

`datum.builder.enabled` is on, and without a security chain anyone could build (the start WARNs about exactly that). Who may
do what is Spring Security's (Datum has no access policy): `SecurityConfiguration` names Datum's routes with
`DatumExchangeMatchers` and gives `builderWrites()`, `builderReads()` (the author's copy), `dryRun()` and
`inspect()` to `ROLE_FORM_ADMIN`; public pages, submissions, PDFs and receipts are open. People sign in with HTTP Basic:
`author` / `author` is a form admin, `viewer` / `viewer` is not (users are in memory; a real application brings its own). The
builder's writes need a CSRF token (cookie `XSRF-TOKEN`, header `X-XSRF-TOKEN`). `DatumServerSecurityResponses` answers the
refusals in JSON: `401 unauthorized` for a visitor, `403 access.denied` for a write without the role; with it the body is
judged (422 for a bad definition).

## Configuration

See `application.yml`. Keys: `datum.pdf.fonts`, `datum.pdf.signing.{ssl-bundle, retired-certificates, trust-anchors, tsa.*}` (the signing key is a Spring Boot SSL bundle,
`spring.ssl.bundle.jks.pdf-signer.*` here), `datum.pdf.seal.*`. A setting that cannot be used (an unknown
font pack, an unreadable signing bundle) stops the start naming the property. `/actuator/health` carries the `pdf` check and
`/actuator/info` the capability.

The test (`PdfExampleIT`) runs the setup script with this JDK's `keytool`, boots the application with the real runtime and
walks the whole story over HTTP.
