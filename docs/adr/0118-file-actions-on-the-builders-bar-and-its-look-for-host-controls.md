# ADR 0118: File actions on the builder's bar, and the builder's look for host controls

## Status

Accepted.

## Context

Builder pages put the same controls on the builder's bar: New, Open (import) and Download. Each host drew them its own way, from its own CSS, so they did not look like the bar they sat on and did not follow a builder theme. Each host also carried its own copy of the behaviour: the unsaved-edits guard, a confirmation before the form is replaced, a hidden file input, a message for a file that is not a form, and a Blob download.

The bar is part of the builder, so New, Open and Download should be the builder's own, and the host should be able to switch them. Whatever a host still slots onto the bar should look like the builder's own controls.

## Decision

1. **The builder's file actions live in a menu on its bar, and the builder does the asking.** `<datum-builder>` takes `fileActions: BuilderFileActions | undefined`, a property that updates the DOM and is re-applied when the shell rebuilds. Only supplied actions show: a raw `<datum-builder>` with no `fileActions` shows none. The menu (`[data-file-menu]`, a three-dot "Menu" button last on the bar) holds Save, New form, Open form file… and Download form, each there only when the host supplies it, and the Dark mode item (ADR 0157). The host does what only it knows, and the shape of each action is in [the builder guide](../reference/builder.md) (File actions, "A host that writes the definition itself"):
   - **New** waits for the active document's unsaved-edits guard (`activeController.requestLeave`), then asks, and runs the host's `new()` on the answer. It skips the question only when there is nothing to lose. The shell cannot see what else the host holds (PDF layouts, journeys), so the host's optional `isEmpty()` has the last word.
   - **Open** opens the file picker inside the author's click, because a picker opens only on a user gesture. A file over the size cap (2 MiB unless `maxDefinitionBytes` says otherwise) is refused before any of it is read. The rest is read and handed to the host's `open()`, which checks it and returns the step that puts it in place, or throws (or rejects) with a message. An accepted file goes through the guard, then a question, then the step.
   - **Download** waits for the guard too, since an edit still in the inspector is not in the file yet. It saves what the host's `download()` returns as a Blob. Where there is no `URL.createObjectURL`, the bar says "Downloads are not available here." instead.
   - **Save** is the host's alone, since only the host knows where a form goes. The builder asks about unapplied edits first, then calls `save()` with the languages changed since the form was loaded or last saved. While its promise is pending the item says "Saving…" and is disabled, so a second save cannot start.
   - Each completed action clears the message and dispatches `builder-file-action` (bubbling, composed) with `{ action: "new" | "open" | "download" | "save", name? }`; `<datum-form-builder>` re-emits it as `datum-builder-file-action` (decision 2).
   - The question is a modal `dialog.db-confirm` in the shell's shadow root (ADR 0179, decision 2; where `showModal()` is missing it opens by the `open` attribute and is answered the same way), and the message about a file is a `role="alert"` box beside the menu, outside it, so it stays in view once the menu is put away. The menu carries no line about publishing: the builder has no publishing page of its own to name, and a host that wants a link adds its own control through the bar's `publish` slot.

2. **`<datum-form-builder>` supplies its own actions, over the whole definition.** The engine shell knows the tree, the localization and the identity. The wrapper's `definition` adds the PDF layouts, the journeys and the tests, so the wrapper supplies the actions. The rules of each, and the `file-actions` attribute and `fileActions` override that choose and replace them, are in [the builder guide](../reference/builder.md) (File actions) and the attribute reference.
   - **New** starts a form under a fresh neutral id (so a download is not named after the last form) with an empty root holding one Submit button, so the form can be sent as it stands. It drops everything else.
   - **Open** refuses what the builder could not take: `toFormDefinition` first refuses what is not a definition's outline, then `formDefinitionProblem` (`support.ts`) walks every component node, requires the root to be the form, and checks the shapes of `localization`, `pdf` (each layout by `validatePdfLayout`) and `journey` (each journey by `validateJourneyShape`), and each refusal says where the problem is.
   - **New's and Open's steps replace the definition all or nothing, and at once.** The step sets `definition` and flushes on the spot: the builder, the PDF side and the Journeys side all reseed from it. Any reseed holds the builder's `init` change until all three sides are on the new form, so the `datum-builder-change` it becomes carries the new form's tree, PDF layouts and journeys, not the old form's. If the builder cannot take the definition after all, the element reseeds from the definition as it stood, the author's edits since the last seed included; the error goes on to the builder, which shows it, and nothing of the refused file is kept.
   - **`isEmpty`** comes with New, the element's own check that a New loses nothing. It counts no PDF layout at all as empty, because the builder writes none by default (ADR 0044), so every layout is someone's work. It applies to whichever New the page uses. A page can hand in its own, which replaces only this part of the check (the builder still looks at the tree, the form's settings and the languages), or `null` to leave the decision to that look alone.
   - **A Download** with no Save of the page's own is the form's save and marks it clean; with one, it is an export and leaves the saved baseline alone. A form with no submit button downloads anyway, with a notice and a `no-submit-button` warning on the event.
   - **Save comes from the page, in one of three ways.** The wrapper has nowhere to keep a form, so the menu has no Save until the page asks for one. One attribute, `save`, asks: with an address the wrapper sends the form there itself, bare it sends nothing and leaves the storing to the page. Either fires `datum-builder-save` first (cancelable, with `waitUntil`): work handed to `waitUntil` is awaited before the request and its rejection fails the save, and `preventDefault()` leaves the request out. When all of it succeeds the wrapper sets `savedDefinition` to the form as sent, so `dirty` clears with no script and stays set for an edit made while the save ran. A `fileActions.save` function wins over the attribute, fires no `datum-builder-save`, and leaves the saved baseline to the page. The attribute's address is held to the page's origin as the module attributes are (`allow-origins` lists others); an address set through the `save` property (`false`, `true` or an address) is not held to it.
   - **A designer alone keeps them.** `workspaces="pdf"` (ADR 0125) chooses workspaces and nothing else.

3. **Host controls take the builder's look, from a light-DOM stylesheet.** `host-control-styles.ts` exports `BUILDER_HOST_CONTROL_STYLES` and `adoptBuilderHostControlStyles(root)`, from the engine's builder index and from `datum-builder.js`. It dresses a button or select slotted into the bar's slots (`toolbar-start`, `toolbar`, `canvas-actions`, `history`, `comments`, `publish`, `account`) of `datum-builder` or `datum-form-builder`, and a button slotted into `strip`.
   - **Where it goes.** Each builder, `<datum-builder>` and `<datum-form-builder>` alike (the wrapper's slotted children live in its root), installs the sheet once into its own root node when it connects: the document or the shadow root it lives in. It is adopted as a constructable sheet where the browser has them, after the document's own sheets so the builder wins a tie, else a `<style data-datum-host-controls>`; a root whose adopted sheets a host replaced gets it back on the next connect, and it never throws.
   - **Every rule, states included, weighs one element, (0,0,1), through `:where()`** (`:where(datum-builder, datum-form-builder) > button:where([slot="toolbar-start"], …)`). A bare `button {}` reset has the same weight and comes earlier in the cascade, so it loses. Any class of the host's wins, in every state.
   - **What the look is** is the studio look (ADR 0124): the pills, round buttons and circles, the selected fill and the accent fill for `data-builder-primary` that [the builder guide](../reference/builder.md) (Toolbar slots and host controls) describes. Every colour and size comes from an existing `--db-*` token, which the slotted control inherits through the flat tree.

## Reasoning

- **`::slotted()` rules in the shell for host controls were rejected.** For normal declarations the outer tree's rules beat a `::slotted()` rule whatever its weight, so any page reset (Bootstrap's reboot, normalize) wins: a probe rule asked for 11px corners, 12px type, a margin, uppercase and a red border, and the page's reboot kept 0px corners, 16px type, no margin and no transform. A stylesheet in the host's own root, held to one element's weight, is the only place that loses to a class of the host's and wins over a bare reset.
- **A builder-owned Download over what the engine shell knows was rejected.** The shell sees the tree, the localization and the identity. The PDF layouts and the journeys live in the wrapper, or in the host's own state for the raw element, so the file would silently lose them. Re-seeding goes through the wrapper for the same reason. So the host supplies the actions, and the wrapper, which holds the whole definition, supplies defaults.
- **Save has a declarative form because the common save is one request.** A page that only stores the definition at an address needs no script for it, as a form's `draft-store="server:<url>"` needs none. The request is plain on purpose: the page's own headers, credentials on another origin and a revision check are the page's decisions, and the event and the function are where it makes them. One event serves both forms of the attribute, in the shape of `datum-submit`'s `waitUntil`, so a page adds a step before the request, or takes the storing over, without a second mechanism. One attribute rather than two because both add the same menu item and shortcut and fire the same event; an address is the only difference.
- **The attribute's Save sets the saved baseline; the function's does not.** With `save` there may be no script to call `markSaved()`, and a Save that left the form marked unsaved would be wrong on its face. A page that hands in a function usually knows more about what saved means (a revision, a translation catalog to update first), so the baseline stays with it.
- **New `--db-*` tokens for host controls were rejected.** Every builder theme would have had to set them (ADR 0124's exact coverage), and the bar button's tokens already describe the look.

## Consequences

- **One implementation.** New, Open, Download and Save, the guard, the question, the refusal and the download exist once. Every page that embeds `<datum-form-builder>` gets them without code. A page that wants none says `file-actions="off"`.
- **A button or select a page already slotted onto the bar draws in the builder's look, under every builder theme.** A page that styled it by class keeps its own look, because a class outweighs the sheet. A page that styled it through a bare `button {}` or `select {}` rule does not; that is the point.
- **A long refusal is cut short on the bar.** V8's JSON error quotes the text it choked on, so a message can run long; it keeps to one line with an ellipsis, whole in its title and to a screen reader.
- **Token coverage is unchanged.** `host-control-styles.ts` reads only `--db-*` tokens the studio token list already declares, so a builder theme that sets them dresses the host's controls too.
